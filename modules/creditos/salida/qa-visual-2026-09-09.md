## 1. Comportamiento end-to-end (circuito de créditos)

Recorrido: **cliente → solicitud → aprobar → originar → lote → desembolso.**

- ✅ Alta de solicitud (backoffice) para cliente registrado: crea `SOL-...` en BORRADOR; "Enviar a evaluación" → EN_EVALUACION.
- 🔴 **BLOQUEO (single-admin): la solicitud NO se puede aprobar.** El workflow **SOLICITUD** (cuatro-ojos)
  está activo y su nivel "Aprobación" **exige rol ADMG**. El único ADMG es `admin`, que **no puede aprobar
  lo que él mismo creó** (separación de funciones). `creditos` (XCR) tampoco puede (el nivel pide ADMG),
  aunque tenga `sinRestricciones`. → Con un solo usuario, una solicitud cargada desde backoffice queda trabada.
  - El **portal NO sufre esto**: la solicitud la crea el ciudadano (`portal:<sub>`), así que admin sí puede aprobarla.
  - Mismo patrón con el workflow **LINEA**: publicar una línea nueva/revisada (p.ej. "Adelanto de Haberes",
    hoy EN_REVISIÓN) requiere aprobación ADMG del no-emisor → también se traba con un solo admin.
- ✅ Con el workflow SOLICITUD desactivado (prueba temporal, restaurado después): aprobar → APROBADA →
  originar → **A_LIQUIDAR** → liquidar lote → **ACTIVO** (desembolsado). El resto del circuito es sólido.

**Decisión (aplicada):** se optó por **(a)**: `seed_workflow` ahora siembra **LINEA y SOLICITUD inactivos**
(DESEMBOLSO/REFINANCIACION ya lo estaban). Un único admin opera de entrada; el cuatro-ojos se activa desde
Seguridad → Workflow cuando la org suma un 2º aprobador. La base actual quedó con los 4 workflows inactivos.
Re-verificado E2E como admin: crear → **aprobar** → originar → lote → **desembolso** → ACTIVO, sin bloqueo.

## 3. Auditoría de validaciones / obligatorios (resumen; detalle del sub-informe)

🔴 = obligatorio de negocio sin gatear · ⚠️ = falta validación de formato

- **Clientes.tsx**: ⚠️ DNI (solo `maxLength`, acepta letras), email (sin formato), sueldo (sin `≥0`),
  CBU (sin 22 díg). Front valida CUIL por longitud pero el backend valida el **dígito verificador** →
  un CUIL de 11 díg con DV malo pasa el front y da 422. Ningún campo con asterisco.
- **SolicitudesCredito (express)**: 🔴 el front dejaba avanzar sin CUIL pero el backend lo exige (422). CUIL/DNI sin filtrar. → **corregido** (§4).
- **Backend `SolicitudIn`**: 🔴 `monto_solicitado`/`plazo_solicitado` sin `gt=0`. → **corregido** (§4).
- **OriginarCredito**: 🔴 CBU sin filtrar/validar y "Otorgar" no lo exigía → se podía originar/desembolsar sin CBU en originación directa. → **corregido** (§4). CUIL/DNI del paso 1 sin formato (pendiente).
- **Portal**: ✅ CBU + consentimientos gateados. ⚠️ edad (18-99) y sueldo (`>0`) son `min/max` HTML "blandos" y el backend no los revalida (impacto bajo; pendiente).
- **ConfigurarCreditos**: ✅ el mejor validado (doble malla front `compErrores` + backend `_validar_cfg` + integridad al publicar).

Zonas ya bien hechas (no tocar): Portal CBU/consentimientos; modal "Dar de alta en maestro" (CUIL 11+DV, H-137);
ConfigurarCreditos; rangos monto/plazo/tasa en Originar y wizard PP; grilla "Revisión para liquidar" (H-134).

## 4. Correcciones aplicadas en esta pasada (H-141)

1. **Backend `SolicitudIn`**: `monto_solicitado = Field(gt=0)`, `plazo_solicitado = Field(gt=0, le=240)` (paridad con el legacy).
2. **SolicitudesCredito wizard (express)**: se exige **CUIL (11 díg)** en el paso 1 (gate + input solo dígitos + hint), alineado con el 422 del backend; DNI solo dígitos. **Asteriscos** en obligatorios (Cliente/Nombre/CUIL, Línea/Monto/Plazo).
3. **OriginarCredito**: **CBU de acreditación obligatorio** (solo dígitos, 22, hint) y "Siguiente" del paso "Datos adicionales" gateado → no se origina sin CBU válido (cierra el hueco de H-134 en la originación directa).
4. Estilo global `.req` (asterisco rojo) para marcar obligatorios.
